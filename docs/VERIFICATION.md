## Important behavior limits

- **Capacity means known sessions, not the entire backlog.** Unestimated, partly scheduled or waiting work can still require substantial future effort. Thin project spans add no reserved minutes. The “Not fully scheduled” warning must be considered alongside any open-time number; an apparently free day is not a promise that all commitments fit.
- **Effort is explicit.** “Monday through Tuesday” describes a window, not sixteen hours of work. Missing/ambiguous effort or dates must be clarified. Finish this day subtracts that day's booked hours from known remaining effort; the advanced individual-session completion control leaves reported effort unchanged. Neither action changes the original estimate or automatically completes the project. Time passing does not complete work.
- **Planning is bounded and greedy.** The deterministic allocation rules search a horizon of up to 366 days from the eligible start, constrained by deadlines, allowed dates, focus blocks and existing sessions. They preserve existing commitments where possible; they are not a global optimization solver. A reported conflict means this planner did not find an allowed fit, not a mathematical proof that no possible rearrangement exists.
- **Demo is not AI or delivery.** Typed demo examples support a limited grammar. Recorded demo transcription is unavailable rather than fabricated. Cached/mock model outputs test safety boundaries, not model quality. Captured mail is visible test data and is not sent or replayed later automatically.
- **Current CI has no cloud dependency.** It runs Node 24, locked installation, lint, typecheck, unit/server tests, build and isolated Chromium demo workflows. It does not run a hosted Supabase database, a paid model, real email, Railway deployment, or restoration. Local database/Edge tests are a distinct manual gate.
